# 简易多智能体平台

这是一个**用来理解"什么是多智能体"的最小可运行示例**。

它不追求功能完整，只做一件事：用 4 个角色处理一次机房告警，让你在控制台里直接看到多智能体是怎么分工、通信、协调，最后共同完成一个任务的。

所有工具都是**模拟实现**，只返回固定字符串，不会发起任何真实网络请求或运维操作。

---

## 先跑起来

```bash
cd multi_agent_demo
python main.py
```

默认运行**黑板协作**模式——这是最容易看清"多智能体"的一种方式。

默认只输出关键步骤（谁做了什么、最终结果）。想看完整黑板变化和汇总过程，加 `--verbose`：

```bash
python main.py --verbose
```

其他模式：

```bash
python main.py centralized     # 中心化编排
python main.py hierarchical    # 战略—战术分层
python main.py pipeline        # 阶段/任务域分解
python main.py all             # 四种依次跑一遍，便于对比
```

只需要 Python 3.10+，不需要安装任何第三方包。

---

## 这个场景在做什么

总任务：**A-12 机柜温度过高，请定位原因并完成处置。**

四个角色，各有自己的局部目标和工具：

| 角色 | 职责 | 可用工具 |
|---|---|---|
| 监控员 | 发现告警，只报事实 | `get_alarms` |
| 诊断员 | 结合资产和指标定位原因 | `get_asset`、`get_metrics` |
| 处置员 | 执行处置并创建工单 | `migrate_service`、`open_ticket` |
| 汇报员 | 汇总成事件报告 | 无 |

关键点：**监控员不诊断，诊断员不处置，处置员不重新诊断。** 每个角色只做自己那一段——这就是"角色边界"。

## 什么是一个智能体

一个智能体通常包含三部分：

1. **角色**：它是谁、负责什么、边界在哪；
2. **工具**：它能调用哪些能力；
3. **大脑**：它如何根据观察做决定。

在本代码里：

| 概念 | 代码位置 |
|---|---|
| 工具 | `framework.py` 的 `Tool` |
| 智能体 | `framework.py` 的 `Agent` |
| 大脑 | 一个 `(agent, task, context) -> str` 函数 |

默认使用**脚本化大脑**：每个角色的决策是写死的 Python 函数，不调用大模型。这样做的好处是结果稳定、过程透明，方便你观察协作本身，而不是观察模型输出。

一个智能体的基本循环是：

```
观察（拿到任务和上下文）
  → 决策（决定调用哪个工具、说什么）
  → 行动（调用工具）
  → 把结果写回共享状态
  → 下一个角色继续
```

---

## 什么是多智能体

按你的笔记，判断一个系统是不是多智能体，看四个条件。这个 demo 逐条对应：

| 条件 | 在这个 demo 里 |
|---|---|
| 存在多个角色或智能体实例 | 监控员、诊断员、处置员、汇报员四个 `Agent` |
| 角色之间存在通信或共享状态 | 所有角色读写同一块 `Blackboard` |
| 角色之间有分工、协作或协商 | 调度器按黑板状态决定下一步；每个角色工具白名单不同 |
| 多个角色服务于同一个整体目标 | 都在处理同一个 A-12 告警 |

**仅仅并行调用同一个模型四次，不算多智能体。** 必须同时具备分工、通信和协调，才构成多智能体系统。

## 怎么读黑板模式的输出

运行 `python main.py`，你会看到这样的过程：

1. 黑板初始只有任务；
2. 调度器看黑板，发现缺少 `alarms`，派**监控员**；
3. 监控员调用 `get_alarms`，把结果写成 `FACT: alarms = ...`；
4. 调度器再看黑板，发现缺少 `cause`，派**诊断员**；
5. 诊断员查资产和指标，写入 `FACT: cause = ...`；
6. 调度器派**处置员**执行处置；
7. 调度器派**汇报员**写报告；
8. 调度器看到 `report` 已存在，输出 `DONE`。

注意三件事：

- 智能体之间**没有直接对话**，全部通过黑板间接协作；
- 调度器**不关心谁说了什么**，只看黑板上缺哪个 key；
- 黑板上的每条记录都带 `kind`（FACT / INTENT / HINT）和作者。

这就是"共享状态 + 事件驱动"的最小形态。

## 四种协作方式

同一批角色，可以换不同的组织方式。代码里都实现了，方便对比：

| 模式 | 一句话 | 特点 |
|---|---|---|
| 黑板协作（默认） | 角色只读写黑板，调度器看状态派活 | 耦合最低，最容易观察协作 |
| 中心化编排 | 总控规划任务，分派给角色，最后汇总 | 控制清晰，但总控容易成为瓶颈 |
| 战略—战术分层 | 指挥官分给两个小队，小队内部再编排 | 适合任务较多、需要分层决策的场景 |
| 阶段/任务域分解 | 监控 → 诊断 → 处置 → 汇报，靠共享状态衔接 | 流程清晰，但前一阶段错误会往后传 |

建议阅读顺序：**先看 blackboard，再看 centralized，最后看 hierarchical 和 pipeline。**

## 接真实大模型（可选）

默认不需要 API key。想换成真实 LLM：

```bash
# Windows PowerShell
$env:OPENAI_API_KEY="sk-..."
python main.py --llm --model gpt-4o-mini
```

也支持兼容 OpenAI 接口的本地服务：

```bash
$env:OPENAI_BASE_URL="http://localhost:8000/v1"
python main.py --llm --model Qwen2.5-7B-Instruct
```

接 LLM 后，角色说明会作为 system prompt，工具调用走一个极简 ReAct 循环。

## 已知的简化

这是教学用最小实现，刻意省略了生产系统需要的东西：

- 没有并发，所有调用串行；
- 没有重试、超时、限流；
- 没有持久化记忆，`Agent.history` 只存在内存里；
- 没有权限控制，工具隔离只靠 `Agent.tools` 白名单；
- 没有真实的资产、监控、工单系统，工具全部是模拟的；
- LLM 模式依赖模型严格遵守 `TOOL:` / `FINAL:` 和 `角色名: 子任务` 的格式。

这些正好是你后续做实验时可以逐项加上的变量。

## 和机房数据融合平台的关系

这个 demo 只解决"多个智能体怎么组织协作"，不涉及数据从哪来。

它里面的黑板，就是后续"统一视图"的雏形；把 `get_alarms`、`get_asset` 这些模拟工具，换成融合层提供的 `resolve`、`neighbors`、`metrics`、`explain`，再把黑板换成带证据和版本的统一视图，它就离真实的机房智能运维平台近了一步。
